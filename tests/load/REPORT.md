## P0-7d2 位置写入重试复测（2026-11-20）

单机回环使用 Node 24.22.3、临时 MySQL 8.0.46 和 Redis 8.10.3。改动前后各跑两轮，均使用一个 Node 服务、60 个 MySQL 池连接上限、16 个发压进程和合成账号。冷启动同批发起 2,000 个连接，集中重连关闭 2,010 个已入房连接的底层传输。各轮均在观测结束后收齐对应连接。

客户端每 5 秒计划一个样本。接入期包括首次入房前或集中断开后尚未重新入房的时间，以及连续在房不足 10 秒的时间。连续在房满 10 秒后计入稳态。集中断开前的计划样本单列于 JSON 的 `beforeDisconnect`。错误率为未提交样本数除以计划样本数，同一账号和计划时刻的样本只计一次。JSON 同时记录客户端漏报、服务端收包、尝试写入及成功提交。

|---|---:|---:|---:|---:|
| 冷启动接入期 | 4,002 / 5,106 · 21.62% | 4,002 / 5,089 · 21.36% | 4,001 / 5,113 · 21.75% | 4,000 / 5,031 · 20.49% |

- 两轮改动后都达到稳态错误率 <1% 的目标。自然接入场景中，进入写入的样本全部提交，位置 `DB_BUSY`、池预算拒绝及排队超时均为 0，MySQL 实占峰值为 40–43/60。冷启动漏报率两轮均小幅下降，差异来自尚未入房的样本数。重连接入期一轮上升、一轮下降，漏报主要发生在传输关闭到重新入房之间。
- 第 1 轮改动后和第 2 轮改动前的冷启动，发压端事件循环 P99 峰值分别为 216 ms 和 184 ms，超过夹具的 100 ms 饱和阈值。两轮自然场景的写入结果均为 0% 失败，接入期漏报的变化无法归因于写入重试。

### 瞬时写入故障注入

在 2,010 人已入房的 15 秒窗口，夹具对固定两组合成账号分别在写入前拒绝第 1 次，或拒绝前 2 次写入尝试，模拟 `DB_BUSY` 和排队超时。两轮各注入 1,206 条受影响样本。改动前每轮提交 4,824 / 6,030 条，错误率 20.00%。改动后每轮提交 6,030 / 6,030 条，错误率 0.00%。每轮 603 条经服务端退避后提交，603 条经客户端携带原样本 ID 补发后提交，重复提交为 0。改动后该窗口的可见延迟 P95 为 1.994–2.014 秒。

服务端只保留在途写入和一条可替换的最新样本，自动退避 150–300 ms 一次。忙错误持续时，`live:error` 的第二个参数返回 `POSITION_RETRY_RETRYABLE`、`retryAfter: 1`（秒）和样本 ID。客户端补发一次原样本。服务端按连接的递增样本 ID 和采样时间去重，并淘汰被替换或等待到期的样本。自动重试和客户端补发沿用首次写入时刻。

## P0-7c 当前结论（2026-11-20）

**单机回环稳态实测达到 2000 Socket.IO 连接，2000 猫 + 10 鼠的 2010 连接档也通过 60 秒稳态门槛。该数据不证明“2000 生产级”。** 冷启动与故障恢复仍有位置写入丢失；MySQL 满池期间写入错误率为 29.85%，集中重连 45 秒后仍有 80/2010 个客户端未重新入房。

实现保留 5 秒位置上报，将快照合并推送改为 1 秒；共享玩家状态使用多实例 Redis pub/sub 失效接口，单 Node 也走同一失效接口。SQL 批查询每批最多 64 个账号、最多 6 个并发，1 秒批次期限；查完即释放连接再访问 Redis，批超时跳过本批，单玩家校验失败只跳过该玩家。MySQL 每实例池上限默认 40，连接预算为位置写入 20（队列 256、650ms）、握手 8（96、750ms）、广播 4（32、350ms）、恢复 2（16、500ms）、通用 6（128、2.5s）。握手最多 96 个并发准备请求，溢出返回 503 和 `Retry-After: 1`；H5 重连延迟 2–5 秒并加入抖动。Redis 恢复回填按批限并发，失败重试并退避。未改游戏规则和界面，仅调整 H5 重连时序。

### 瓶颈、配置建议与限制

1. **稳态容量已达到本机目标。** 2,000 与 2,010 档连续 60 秒全连接、0 写入错误，可见 P95 分别为 1.015 秒和 1.045 秒；应用池在用峰值仅 21/40，Node RSS 峰值约 382 MiB。
2. **冷启动仍有短时过载。** 96 个握手并发上限工作正常，未把 2,000 个握手同时压到 MySQL/Redis；但 503 重试把冷启动写入错误压到 5.21% 而非 0，且可见 P99 超过 2 秒。继续保留限流和 2–5 秒抖动，不应直接抬高握手上限。
3. **MySQL 满池时位置吞吐受限。** 40 个连接全部占用后，有限位置队列开始拒绝和超时；应按实例数核算 MySQL 总连接余量，并在部署环境评估 50 连接池是否有数据库预算。优先消除慢查询/锁等待，再重测错误率和可见 P95/P99，不建议仅扩大排队上限。
4. **重连尾部未完全收敛。** 96 接入上限没有触发忙拒绝，发压端也未饱和，80 个未入房客户端伴随 polling XHR 错误。需要在目标接入网络复核 polling→WebSocket 升级和连接错误，并让重连压力持续到全量复入或明确超时；目前不能宣称重连恢复已验收。
5. **Redis 不可用时位置不落库。** 现有策略保留 Socket.IO 房间连接并拒绝依赖 Redis 的请求；如产品要求故障期间也不能丢位置，需要单独设计有界、可过期的最新位置缓冲并补充数据隐私与恢复测试，当前没有绕过 Redis 安全检查。

测试环境为 Windows 11 单机回环：Intel Core Ultra 9 275HX、24 逻辑核、约 32 GiB 内存、Node 24.22.3、MySQL 8.0.46（InnoDB buffer pool 128 MiB）、Redis 8.10.3。所有账号和 MySQL/Redis 数据均为本次临时生成；Steady/cold/Redis 测试使用 4 个同机发压进程，MySQL 满池与重连复测使用 16 个同机发压进程。测试通过不代表独立发压机、学校网络、微信 WebView、多实例或生产 MySQL 配置也达到相同容量。

## P0-7b 修复前基线

## 测试环境与口径

- 实测日期为 2026-11-20，北京时间。Windows 11 单机，Intel Core Ultra 9 275HX，24 逻辑核，约 32 GiB 内存。运行 Node 24.22.3、MySQL 8.0.33、Redis 8.10.3 和 k6 1.5.0。
- 单个 Node 服务进程复用项目的 JWT 握手、Redis 限流、位置读写、清理和 Socket.IO 广播。SQLite 用于冒烟，主场景使用 MySQL + Redis。MySQL 的 InnoDB 缓冲池为 128 MiB，应用池上限为 12 个连接和 256 个排队请求。各服务绑定回环端口，数据库、名单、会话签名密钥和玩家均为本次临时生成。
- 四个 Node 客户端进程按 H5 的默认顺序以 HTTP 轮询握手，再升级到 WebSocket。500、1000、1500、2000 档均含 10 鼠，其余为猫。另测 2000 猫加 10 鼠。玩家每 5 秒错峰上报，全部合成坐标集中在鼠的 300 米可见半径内。虚拟场次固定为首日早场，计时指标使用本机实时时钟。[Socket.IO 传输选项](https://socket.io/docs/v4/client-options/#transports)
- 建连率以实际完成 Socket.IO 命名空间连接的独立账号计。服务端以 1 秒间隔采样同时在线数。断线率以窗口内断线事件除以目标连接数，重连单列尝试与成功次数。
- 写入延迟从计划上报时刻量到 MySQL 提交返回。可见延迟量到另一个客户端第一次收到该条坐标。两者均按成功样本计 P95/P99。上报错误率为未成功写入数除以计划上报数，包含离线、传输丢弃和服务端拒绝。快照应收数按连接数乘以窗口内 5 秒轮次数估算。
- Redis RTT 用服务进程上的 PING 测量，内存取 `INFO memory` 的 `used_memory` 峰值。MySQL 队列峰值和拒绝次数来自应用进程的真实 mysql2 池。Node CPU 以一个逻辑核为 100%，RSS 取窗口内峰值。

## 冷启动与故障

- **冷启动 2000（H5 默认传输，45 秒）**。发压端发出 2000 次首次建连，1,134 个账号至少建连成功一次（56.70%），峰值 1,192，末尾 1,109 入房。建连成功样本 P95/P99 为 4,611/5,104 ms。发生 1,450 次传输断线（72.50%），重连尝试 2,022 次，已有连接的客户端重连成功 46 次。记录到 891 次握手服务繁忙、8,951 次 MySQL 池拒绝及 1,951 次 HTTP 轮询请求错误。最忙的发压进程瞬时用到单核 106% CPU，上报调度 P99 为 104 ms。计划上报 17,979 次，写入 9,177 次（错误率 48.96%），快照 0。
- **k6 冷启动对照（2000 VU，单 VU 运行 40 秒）**。2000 次请求全部发起，396 次完成 WebSocket 升级。128 个升级后的客户端被 Socket.IO 握手拒绝，最终同时在线峰值为 268（13.40%）。已入房客户端发出 2,135 条位置，2,134 条写入，收到 2,144 条快照，可见 P95/P99 为 4,479/4,927 ms。k6 进程采样峰值为单核 56.6% CPU、613.3 MiB RSS。其余 1,604 次失败发生于 WebSocket 升级阶段，具体原因需要在独立发压机复核。k6 结果只覆盖成功入房客户端的实际负载。
- **Redis 重启（2010 连接，45 秒）**。临时 Redis 停止到重新收到 PONG 用时 12.28 秒。应用采到 16 个 Redis 未就绪的秒样本，收到 6,716 次 `RATE_UNAVAILABLE`。Redis 恢复后批量复查打满 MySQL 池，1,742 个客户端收到服务端断开（86.67%），自动重连 0 次，窗口结束仅 268 个仍入房。写入恢复约在 Redis PONG 后 5 秒，整窗写入 4,282/18,090（错误率 76.33%）。剩余客户端收到了 1,072 条快照，可见 P95/P99 为 4,606/4,972 ms。

## 瓶颈与最小改动建议

1. **限制整轮房间校验的数据库并发。** `sendSnapshots()` 每 5 秒对全部在线玩家发起房间复查。仅首批数据库读就能占满 12 个连接和 256 个排队名额。500 档每轮 232 次拒绝，6 轮合计 1392 次，吻合实测。任一次拒绝都会中止这一轮广播。建议先限制广播及恢复任务的数据库并发，为实时写入和握手预留连接，并把单个校验失败限制在相应玩家。保留活动、暂停、安全屋和离线的可见性检查。若批处理时间仍超预算，再合并共享状态查询。
2. **控制恢复阶段的并发和等待。** Redis 恢复时的房间复查和批量 Socket.IO 鉴权也会同时占池。建议给恢复复查分批，给可重试的握手忙状态加入有上限的退避与抖动。保持 Redis 不可用时的上报拒绝策略。
3. **用复测数据决定池和接入配置。** 以 12 连接、256 排队为基线验证上述改动。按实例数和 MySQL 连接预算配置池，并为排队设置可观测的时限。冷启动改用独立发压机，记录 TCP、WebSocket 升级和 Socket.IO 握手，再决定接入队列和限速参数。广播恢复后再测 10 鼠同时读取 2000 个附近猫点位时的 Redis GEO、JSON 扇出和带宽，本轮的满载 Redis RTT 与内存属于广播中断时的负载。
4. **按验收口径调整推送节拍。** 200 连接时 MySQL 写入 P95 为 34 ms，位置可见 P95 为 4,568 ms。若 2 秒门槛用于地图上的可见延迟，需在保留客户端 5 秒上报的情况下缩短服务端广播间隔或改用短批次推送，再复测可见延迟和消息交付率。
